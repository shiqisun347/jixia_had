# Spec 284：实验批次与预约索引分页

- 版本：v2.0
- 状态：本地实现完成，待受保护发布
- 日期：2026-10-13
- 依据：实验管理与参与者入口审计发现批次、预约接口会将全部历史记录一次性读入内存，且预约逐行查询最新 attempt。

## 问题与范围

`GET /api/admin/experiments/batches` 和 `GET /api/experiments/appointments` 原先没有
结果上限。批次或发布历史增长后，一个请求会把全部 ORM 行和响应同时保留在 Core 内存中；
预约接口还会为每一行单独查询最新 attempt，形成 N+1 查询。两条接口增加 `limit`（默认
50、最大 50）和不透明 `X-Next-Cursor`，数据库每次最多读取 51 行；预约的最新 attempt
改为单次批量查询。响应主体继续保持原有 JSON 数组，旧客户端无需改变解析方式；Web 客户端
自动跟随游标读取完整历史。

## 验收

1. 两条接口默认及显式 `limit` 都不超过 50；游标无效返回可理解的 422 错误，不泄露内部 SQL。
2. 返回数组字段和每个对象字段保持兼容；存在后续页时只通过 `X-Next-Cursor` 提供游标。
3. 批次列表使用稳定的 `(created_at,id)` keyset；预约使用稳定的排表键，并在一次批量查询中
   取得当前页所有最新 attempt，不再每行发起查询。
4. Web 端自动跟随游标，既能兼容旧的数组响应，也不会因接口分页而隐藏历史批次或预约。
5. Core 专项测试、契约检查、Web 类型检查和 diff 检查通过；不宣称生产压力或线上发布通过。

## 非目标

- 不改变实验生命周期、排表顺序、attempt 选择规则、权限或数据库结构。
- 不修改既有 migration，不写生产数据库，不重启服务。
- 不处理赛后参与者/专家标注任务接口；这些问题另立规格。

## 回滚边界

仅移除两条索引接口的分页参数、批量 attempt 查询和对应 Web 跟随逻辑；保留实验数据和其他
资源上限。
