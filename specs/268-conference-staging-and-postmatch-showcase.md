# Spec 268 — 会议现场候场、应急控制与赛后展示

- 版本：v2.0
- 状态：已实施、测试并发布；真人现场完整流程仍需现场验收
- 日期：2026-10-11
- 范围：线上卡顿可控项、比赛候场与二次启动、管理员应急抽屉、赛后点评/投票/颁奖/后台展示
- 依赖：Spec 247、259、265、267

## 背景与目标

当前公网访问偶发延迟主要来自客户端到服务器的网络路径波动；服务器没有持续 CPU、内存、磁盘或应用错误。首页首屏仍下载约 1.9 MB 的 PNG，且未使用长期缓存。会议现场还需要把“准备完成”和“正式开始”明确拆开，并让观众和管理员在同一场比赛中拥有不同的展示与恢复能力。

本规格将可由应用控制的卡顿项收敛为压缩、响应缓存和减少首屏传输；网络运营商、VPN 或用户本地链路不在服务器代码可修复范围内。比赛主状态继续由 Core/MatchActor 权威推进，Web 只展示和发送命令。

## 现场比赛流程

1. 管理员创建房间并邀请辩手；八个正式席位完成准备后，管理员点击“进入候场”。房间变为 `START_PENDING_RUNTIME`，所有角色进入比赛页候场视图，主持音和正式计时均未开始。
2. 管理员在比赛页的主持控制区点击“正式开始”。Core 校验管理员/房间组织者权限，经事务提交后进入既有 `START_COUNTDOWN`，倒计时结束才进入 `RUNNING`。刷新、重连或观众加入不得跳过该门。
3. 观众账号可以加入同一房间并打开大屏视图，只接收服务端状态和音频，不获得辩手麦克风或控制权限。
4. 管理员/组织者在比赛页获得固定入口的应急抽屉，复用既有暂停、恢复、重置当前发言、终止和恢复检查能力；所有命令仍串行进入 MatchActor，并显示服务端确认状态。

## 赛后展示

比赛进入终态后，管理员可以在独立的文本型后台页切换当前展示阶段并发布数据。展示页保持辩论页视觉语言，但不显示中央比赛计时器。

- **评委点评**：填写文字点评、最终胜方和最佳辩手；服务端校验最佳辩手属于本场八席。
- **观众投票**：移动端友好；登录观众每场只能提交一次，提交胜方和八位辩手的完整名次。服务端校验八个席位全部出现且不重复，唯一约束为 `(match_id, voter_user_id)`。
- **观众结果**：按投票汇总胜方和八位辩手排名，显示票数与样本量；未发布前不对观众公开后台草稿。
- **颁奖页**：展示观众排名前三和全部八位有序名单，以及评委选出的胜方、最佳辩手和点评。
- **后台页**：管理员/组织者查看投票统计、录入评委结果、切换 `JUDGE_REVIEW`、`AUDIENCE_VOTE`、`AUDIENCE_RESULTS`、`AWARDS`、`CLOSED` 阶段并发布/撤回。

新增数据只追加 migration：`postmatch_showcases` 保存当前阶段和发布状态，`postmatch_judge_entries` 保存评委结果，`audience_votes` 保存每个观众的一次投票及八席名次。历史比赛不回填、不改变原有 JudgeResult 或比赛快照。

## 性能切片

- 将首页 v5 透明插画生成压缩 WebP，并保留 PNG 作为兼容回退。
- 首页使用响应式 `picture`/固定尺寸，避免布局抖动；静态带版本资源返回 `public, max-age=31536000, immutable`。
- 不在 Core 增加轮询或新服务；不得以缓存隐藏比赛状态，比赛实时数据仍走现有 WebSocket/查询策略。

## 验收

1. 房间启动后所有角色进入候场页；未点击正式开始前，MatchActor 保持 `START_PENDING_RUNTIME`，无主持播报、无辩手计时。
2. 只有管理员/组织者可以点击正式开始；重复点击、刷新、重连和观众加入均幂等，且只产生一次 `START_COUNTDOWN`/`RUNNING` 转换。
3. 管理员应急抽屉的暂停、恢复、重置、终止和恢复失败提示均来自服务端；普通辩手和观众看不到控制入口。
4. 纯真人、纯 Agent 和混合八席均可完整进入候场、正式开始、比赛结束；原有 YXH 四辩和主持衔接回归不受影响。
5. 评委可以保存并发布点评、胜方和最佳辩手；非法席位被拒绝。
6. 观众可以在手机宽度完成一次投票；第二次提交返回可操作提示；不完整或重复排名被拒绝；汇总排名稳定且可解释。
7. 管理员切换阶段后，展示页在刷新/重连后仍显示服务端已发布阶段；无中央计时器，文本和结果可读。
8. 通过 Core/Web 定向测试、迁移独立数据库测试、契约、类型、Lint、构建和浏览器门禁；公网健康检查与首页资源大小/缓存头核验通过。

## 回滚边界

回滚只恢复 Web standalone 和 Core/Jobs 代码，并关闭赛后展示入口；新增表保留以避免破坏历史投票数据，旧比赛状态、音频、规则快照和既有 JudgeResult 不修改。若线上有进行中的比赛，发布前必须确认不改变其 MatchActor 状态；数据库 migration 只执行向前兼容的追加建表。

## 实施与发布证据（2026-10-11）

- 性能切片：首页首屏图增加 WebP（约 428 KB，PNG 约 1.8 MB 作为回退），移除 PNG preload，带版本 WebP 返回一年 immutable 缓存；线上首页 HTML 36 KB、WebP 200 且 `Content-Length: 438000`，公网首页 200，观测 TTFB 约 0.29 秒。
- 现场切片：新增 `prepare-match`，房间启动只创建 `START_PENDING_RUNTIME` 候场比赛；比赛页显示候场卡片，只有组织者/管理员点击“正式开始比赛”才进入既有 `START_COUNTDOWN`。旧 runtime-start 客户端保留兼容路径。
- 应急切片：主持人/管理员在实时比赛页获得应急控制台，复用暂停、恢复、重置、终止和正式启动；所有命令仍进入 MatchActor。观众可进入同一实时页并使用大屏模式，不获得控制权。
- 赛后切片：追加 migration `0045_postmatch_showcase`，新增 `postmatch_showcases`、`postmatch_judge_entries`、`audience_votes`；新增评委点评、观众一次性投票与八席完整排名校验、观众结果/前三颁奖、后台阶段切换页面。线上 migration head 已为 0045，三张表存在。
- 本地验证：Python compile、Ruff、MatchActor 113 项回归、赛后 9 项回归、YXH 4v4 模拟、Web TypeScript、定向 ESLint、OpenAPI contract、生产构建通过；Web 生产构建列出四个 showcase 路由。
- 线上发布：Core 重启后 live/ready 200、四服务 active；发布切换期间 Web 曾因制品目录替换出现短暂 3 次自动拉起，随后连续 5 次 Core/Web 健康采样通过且当前服务 active。发布前已有一场 `PAUSED` 比赛，migration 与重启后仍保持 `PAUSED:1`，未终止或改写该比赛。Web standalone 回滚点保留在 `/opt/jixia-web/releases/web-live-20261011014637`、`web-live-20261011014850`，Spec 267 Core 回滚点保留在 `/opt/jixia-spec267-final-20261010233800`。
- 浏览器核验：已登录管理员可见 `/matches/{match_id}/showcase/admin` 的阶段切换、评委表单和八位辩手；投票页在未发布阶段显示禁用状态和八个完整名次选择器；首页 DOM 使用 WebP source。
