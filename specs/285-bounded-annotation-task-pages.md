# Spec 285：参与者与专家标注任务有界分页

状态：本地实现完成，待受保护发布

## 背景

参与者和专家任务列表原先一次读取用户全部任务，并为每个任务逐项查询关联
机会、语音、答案和问卷。历史实验数据增长后，单次响应和 Core 查询数会随
任务数线性放大，容易造成请求超时和内存峰值。

## 范围与验收

- `/api/experiments/annotation-tasks` 和 `/api/experiments/expert-tasks` 使用
  `created_at,id` 降序 keyset 游标分页，默认 25 条、上限 50 条；下一页通过
  `X-Next-Cursor` 返回。`limit` 越界由 FastAPI 以 422 拒绝，非法游标返回
  `experiment_query_invalid`。
- 单页任务的关联对象使用批量 SQL 查询构建响应，避免每个任务触发独立查询；
  页面数据仍保持原有数组响应和字段，现有任务详情、保存和提交接口不变。
- Web 客户端自动消费游标页面并合并数组，旧页面调用方继续获得原数组形状；
  单页响应始终受 Core 上限约束。
- 旧的服务层兼容 helper 仍返回完整数组以保留内部调用语义，但按最多 50 条一页、批量加载
  逐页推进；HTTP 路由始终只返回当前有界页。

## 回滚边界

仅回滚应用代码即可恢复旧数组路由；不涉及数据库迁移或数据删除。发布前后需
观察 Core 查询时延、响应大小、RSS 和实验工作台加载时间；不在生产受保护窗口
之外执行数据库写入或服务重启。

## 验证证据

- `apps/core/tests/test_experiments.py`：游标编码/解码及非法游标回归。
- Core experiments service/routes Ruff、Pyright 通过；实验单元测试 9 项通过。
- 真实 PostgreSQL 分页和查询计数应在受保护测试数据库中执行；本地生产环境未写入。
