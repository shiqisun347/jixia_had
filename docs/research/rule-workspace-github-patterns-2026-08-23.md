# 赛制规则工作台 GitHub 设计调研

调研目标是解决现有赛制页面把元数据、阶段、主持文本、动作和删除操作平铺在一个长表单中的问题，
并为规则私有 Agent 池选择清晰的信息架构。调研只借鉴交互模式，不复制项目实现，也不引入新的后台框架。

## 参考项目

| 项目 | 采用的模式 | 不采用的部分 |
| --- | --- | --- |
| `directus/directus` | 列表与记录详情分离；复杂关联记录在抽屉中编辑 | 动态数据模型和扩展运行时 |
| `payloadcms/payload` | 编辑工作区有稳定导航、保存状态和字段级错误 | CMS Schema 和版本发布工作流 |
| `n8n-io/n8n` | 选择流程节点后编辑该节点配置 | 自由画布、连线、分支和通用工作流引擎 |
| `refinedev/refine` | 加载、失败、脏表单、提交和失效刷新语义 | Refine 运行时和第二套 CRUD 抽象 |

## 结论

赛制管理采用“规则目录 → 规则工作台 → 阶段配置抽屉”。阶段流程只是一条可排序的线性时间线，
不伪装成通用流程图。规则工作台使用基本信息、阶段流程、Agent Prompt、AI 裁判、校验与启停五个稳定页签。
Agent 管理先选择规则，再加载该规则的 Agent 池；编辑弹窗只包含模型、状态、折叠生成参数和一个 Prompt 槽位。

继续复用现有 `AdminShell`、TanStack Query/Table、Dialog、Drawer 和表单控件。这样既获得成熟后台的任务分层，
又避免引入 Refine、React Admin、SQLAdmin 或另一套权限、缓存和错误语义。

## 可验证标准

- 规则目录不展开编辑表单，阶段详情不占用主页面纵向空间。
- 选择一个阶段即可定位其动作、主持词和 Prompt，不需要在整页搜索字段。
- Agent 页面不存在跨规则混合列表，也不提供复制、手工新增或手工删除。
- 保存失败保留输入；脏状态、字段错误、危险确认、键盘排序和三个桌面视口均有测试证据。
